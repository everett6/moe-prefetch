# Plan R: real prompts, coding and decision-making

## Why this plan exists

Every number in this repo was measured on prompts I wrote myself.
`experiments/corpus_prompts.py` is 16 registers of my own templates crossed with
my own topic lists. It is internally varied and it is still synthetic: short,
uniform, instruction-shaped, and free of the thing real coding work is mostly
made of, which is a large block of somebody else's code pasted in.

That matters in two directions, and the second is the one that should worry me:

1. the predictor was trained on it, so it learned synthetic routing
2. **the benchmark was run on it**, so 118.2 tok/s is a statement about
   synthetic workloads, not about coding

Rule 3 says do not overfit the benchmark. A synthetic benchmark is the strongest
possible way to do exactly that, so R3 below re-measures throughput on real
prompts before any model work happens. If the headline number does not survive
contact with real coding traffic, that is the finding, and it outranks anything
the predictor does.

## Standing result this plan has to respect

E5 measured that at the current upload cost a *perfect* predictor is worth
**-0.4 tok/s**. That verdict was reached on the synthetic corpus. Real coding
prompts differ in precisely the dimensions the verdict depends on -- context
length, prefill/decode ratio, routing entropy, expert reuse across a long code
block. So E5 gets re-run on real traces (R6) rather than assumed. I expect it to
survive. I have been wrong about that class of expectation before, which is why
it is measured instead of asserted.

### Leakage
The split unit is the **group**, not the prompt. A held-out SWE-bench repo is
unseen code in an unseen project; a held-out Stack Exchange site is a different
community with different vocabulary. This is strictly stronger than the old
register split, where train and test were two halves of the same template.
LOCKED TEST groups are chosen before capture and never reassigned.

## Steps

- **R1** Fetch. Resumable, cached, checksummed, one JSONL per source, manifest
  with counts and sha256. Cap length, record the cap.
- **R2** Characterise real vs synthetic: token lengths, prompt shape, how much
  of a real coding prompt is pasted code. Show the difference is real.
- **R3** **Re-measure end-to-end throughput on real prompts** at the current best
  config. Does 118.2 +/- 1.66 hold? Same statistical protocol: interleaved, n>=10.
- **R4** Capture routing on real prompts. Dataset v4, new version id, same
  sharded/resumable/validated harness.
- **R5** Retrain from scratch on v4, group-held-out locked test.
- **R6** Re-price the economics on real traces: upload cost, break-even
  precision, E5 oracle ceiling.
- **R7** Integrate if it wins on real workloads; report plainly if it does not.
- **R8** Tests, docs, honest commit.

## Stopping condition
R3 and R6 decide it. If real workloads do not change the economics, the model
work stops at R5 with a measured negative result recorded, and the throughput
finding from R3 becomes the deliverable.

## Corrections made while executing

Recorded here rather than quietly fixed, because both were my own errors and
both would have produced a confident wrong claim.

**R3 control placement.** The first version ran the control prompt once, at the
start of each pass. The expert cache is a server-lifetime LRU, so the control
met a colder cache than the 23 real prompts that followed it — and "real prompts
are faster" would have been indistinguishable from "later prompts are faster".
The control now runs first, middle and last in every pass.

**R3 prompt ordering.** The bench set is built stratified by length band, which
put every long prompt late in the pass. Length and recency moved together, so
any length effect was confounded with cache warming. Prompts are now shuffled
per round.

**Position subsampling destroying the strongest feature.** Caught before the
capture ran, not after. See `docs/REAL-DATA.md`.
